# 续火花前端重设计调研

日期：2026-11-14。阶段：资料调研与问题诊断，尚未选定最终视觉方案。

## 1. 目标与调研范围

用户授权推翻现有视觉与页面组织方式，要求保留具体功能，先调研，再制作预览图。本轮仅形成研究材料，不生成预览图，不修改现有 UI 或运行配置。

研究依据：现有首页的浏览器实际渲染、`ui/static/index.html` 当前页面与交互结构、PRODUCT.md、DESIGN.md、好友规则与人工核对文档，以及下列产品的官方设计文章、产品展示和操作文档。外部产品未登录实测；对其体验的判断限于公开材料，不能视作完整可用性测试。

## 2. 现有界面诊断

以下是本项目的设计判断，而非外部资料的结论。

1. **导航视觉重量偏高。** 深蓝色整列侧栏占据较强注意力，选中项又叠加亮蓝底；首页主体的操作重点相对分散。
2. **同一结果表达多次。** 首页同时使用“今日已完成”徽标、已发送比例、百分比、满进度条、好友成功状态、最近运行成功数。信息有各自价值，但首屏强调过于平均。
3. **容器层级多于内容层级。** 大卡片里又嵌最近运行和下次执行小卡片，加上图标底板、徽标、编号圆底，形成较多框与底色。
4. **正常状态占据空间多。** 成功结果仍占用最大的展示区域；待核对、登录异常等真正需要处理的状态应有明确优先级。
5. **页面结构相似。** 好友名单、消息编辑、时间配置、运行历史属于不同任务，却大多使用“页面标题 + 卡片标题 + 卡片内容”的相同表达。
6. **中文界面需要单独排版。** 外文参考中的小字号、紧行高和大写标签不能直接迁移；中文昵称、长消息、状态说明需要实际验证。

重设计的价值应体现为：主体更清楚，状态更容易判断，常用操作更好找，同时保留完整功能。

## 3. 官方案例与可迁移原则

### Linear：复杂工具的界面秩序

来源：[A calmer interface for a product in motion](https://linear.app/now/behind-the-latest-design-refresh)，2026-03-12。

- 官方文章讨论功能逐渐增加造成界面拥挤，以及通过降低侧栏显著性、统一页头和操作位置改善一致性。
- 对本项目的启发：降低侧栏的颜色和面积存在感；统一标题、账户上下文、页面操作的位置；筛选与内容直接关联。
- 适用区域：应用框架、好友列表、运行记录。
- 适配边界：本项目操作量小于大型项目管理工具，不能照搬高密度小字和复杂层级。

### Things：围绕今天的任务组织内容

来源：[Things features](https://culturedcode.com/things/features/)。该页面包含 Things 3 最初设计介绍，并非全部描述最新版本。

- 官方设计将 Today 作为日常活动入口，把日程与待办组织在同一视图；编辑条目的额外字段按需出现。
- 对本项目的启发：首页先回答“今天完成了吗、有没有事情需要我处理、下次什么时候运行”；复杂的好友专属规则在进入编辑后展开。
- 适用区域：首页、好友详情、首次使用。
- 适配边界：大量留白适合低密度概览；好友多时仍需要高效列表，不能把每位好友做成巨大的展示卡。

### Notion Calendar：时间与设置的清楚关系

来源：[Notion Calendar](https://www.notion.com/product/calendar)。

- 官方展示将查看日程、安排时间、时区和快捷操作作为主要使用场景。
- 对本项目的启发：让“每天何时运行”“下次执行”“历史结果”在任务页形成顺序；时间设置不需要与历史统计争夺注意力。
- 适用区域：自动任务页、下次执行摘要。
- 适配边界：本项目只是每天定时运行，没有必要引入复杂周历、拖拽排期或多个日历功能。

### Raycast：操作与当前对象关联

来源：[A fresh look and feel](https://www.raycast.com/blog/a-fresh-look-and-feel)，2022-07-19；[Action Panel](https://manual.raycast.com/action-panel)。前者是历史设计案例，后者是当前公开操作文档。

- 设计文章解释搜索、操作栏和统一图标的调整；操作文档区分主操作与分组的上下文操作。
- 对本项目的启发：好友行突出常用操作，其余管理项分组；页面主操作位置固定；运行状态的反馈靠近触发动作。
- 适用区域：好友行、详情面板、发送确认、操作反馈。
- 适配边界：不把关键功能藏在只能通过快捷键打开的菜单中；人工核对入口保持可见；本次不新增命令面板功能。

### n8n：自动化记录的可追溯性

来源：[View all executions](https://docs.n8n.io/workflows/executions/all-executions/)。

- 官方记录列表支持按状态和执行时间筛选，并将执行详情与重试关联。
- 对本项目的启发：运行记录采用清楚的时间、方式、结果和逐好友详情结构；失败与不确定结果应区分。
- 适用区域：历史列表、运行详情、人工核对。
- 适配边界：只借鉴信息组织。本项目的防重复发送与人工核对流程必须保持，不能套用通用的“一键重试整批”。

## 4. 对本项目的初步设计建议

以下均为研究后的候选判断，尚未锁定配色、布局或导航方案。

### 视觉基调

- 主体采用清楚的浅色工作面和深色正文，用字体、对齐和间距建立层级。
- 品牌色集中在少数主操作、选中项和识别细节；状态色按成功、进行中、待核对、失败分别使用。
- 可探索暖白与少量橙色，使“续火花”具有亲近感；也保留中性灰和克制冷色的方向进行比较。橙色品牌与警告色必须能够区分。
- 标题、正文、辅助信息保持有限而稳定的层级；中文正文以约 14–15px 为起点验证，不能为追求密度牺牲可读性。
- 统一图标笔画、圆角和控件尺度，减少为普通信息额外添加的底板。
- 只在编辑、状态改变和操作反馈时使用短动效。

### 页面结构

| 区域 | 候选结构 | 重点 |
| --- | --- | --- |
| 今日概览 | 一条明确结果、下次执行摘要、需要处理的事项、精简好友进度 | 正常时安静，异常时指出下一步 |
| 好友管理 | 可搜索筛选的名单，进入好友后编辑规则 | 清楚看到对象、状态和操作归属 |
| 消息管理 | 集中的文字编辑区与图片素材区，旁边解释现有发送规则 | 让编辑内容成为视觉主体 |
| 自动任务 | 时间设置为主，本周结果与近期记录为辅 | 分清已保存计划与实际运行结果 |
| 登录与记录 | 登录状态与记录采用明确分区；可比较页内分栏或标签形式 | 既能判断登录情况，也能快速找记录 |
| 多账户 | 总览与账户切换分工清楚，始终标明当前账户 | 防止配置和发送操作作用于错误账户 |

首屏应根据状态调整：未登录时引导登录；待执行时显示计划和准备状态；运行中显示进度和停止；完成后显示结果与下次计划；出现失败或待核对时显示对应入口。页面组织可以改变，运行规则不变。

## 5. 功能保留清单

以当前前端源码为主，相关产品文档用于解释行为。后端存在的功能不等于当前前端已提供入口，制作全套方案前需逐项核对。

- 首页：今日真实进度、最近运行、下次执行、立即发送、试运行、运行中停止、好友结果摘要。
- 好友：添加、搜索、状态筛选、改名、删除、从聊天列表选择导入；导入结果中的火花天数仅在有来源证据时展示。
- 好友规则：暂停与恢复、默认或专属消息、专属文字与图片、固定/随机/轮换/全部发送、节日祝福开关。
- 消息：编辑默认候选文字、上传和移除候选图片、保存和现有规则说明；维持现有文件类型、数量与体积限制。
- 自动任务：每日时间、保存反馈、下次执行、本周结果、最近自动运行。
- 登录：检查登录、扫码、导入凭证、清除凭证；区分没有凭证、未验证、检查可用、需登录、安全验证和检查未完成。
- 运行历史：发送与试运行筛选、日期与结果查询、分页、逐好友详情、单条补发的类型区别。
- 待核对：确认已发送、确认未发送、条件满足后只补发这一条、查看人工处理记录。
- 多账户：新增、切换、改名、启用/停用、扫码、移除；账户数据隔离，新账户默认停用。
- 通用：首次引导、加载、空列表、错误、保存反馈、运行锁定、危险动作确认、键盘焦点和窄屏操作。

README 中的导出/备份、通知等描述与当前页面入口未完全一致；应单独核对后标为“需保留的已有能力”或“仅文档记载”，不能在预览中擅自增删。

必须保持的行为包括：试运行不计入真实发送；当天发送去重与配置快照；不确定结果需人工判断；修改消息的生效时机；暂停立即生效；账户与登录状态不混用；凭证原文不外显；定时计划存在不代表未来一定能执行。

## 6. 后续预览阶段的评估要求

后续应先比较结构与视觉表达差异明显的方向，再挑选一个扩展。当前不作最终风格决定。

- 首批预览至少覆盖首页、好友列表与规则编辑、消息编辑，以检验同一设计能否承载不同任务；其余页面随后完整覆盖。
- 桌面与手机分别考虑导航和密度；手机不直接压缩桌面表格，不把六个长标签机械挤在一排。
- 需包含正常完成、运行中、待核对、首次使用或空状态，避免只做一张理想成功状态的漂亮首页。
- 使用明确标注的匿名演示数据，验证长昵称、长文案、少量与较多好友；不得把真实好友和凭证上传给外部设计服务。
- 判断标准：三秒能否理解今日结果；能否辨认当前账户；能否找到发送、检查、规则和核对入口；中文是否清楚；异常是否可处理；全部已有功能是否有去处。

## 7. 调研结论

值得迁移的是 Linear 的层级秩序、Things 的今日任务视角、Notion Calendar 的时间表达、Raycast 的操作分组，以及 n8n 的运行记录组织方式。它们服务于本项目的不同部分，不应混成五种视觉风格。

下一阶段要解决的核心是：在统一的视觉系统下，让今日概览、好友名单、消息编辑和执行记录分别采用适合任务的结构。最终色彩与构图通过后续预览判断。
