# 多用户模块 · 设计方案（本地多成员）

> 状态：设计稿，未实现。配套效果图：[`docs/design/multi-user/preview.png`](design/multi-user/preview.png)（源文件同目录 `sheet.html` / `login.html` / `members.html` / `dialogs.html`）。
> 结论：**能做，不需要推翻现有架构**。真正的工作量不在页面，而在「数据分区 + 定时任务按成员排队」这两处后端改造。

---

## 1. 一句话结论

在一台电脑上支持多人轮流使用：每人一个本地账号和密码，各自拥有独立的抖音账号、好友、消息、凭证和运行记录；管理员可以添加、停用、重置、删除成员；切换成员不退出程序，但要重新输入对方密码。

它**不是**云端多租户，也**不是**安全沙箱：服务仍然只监听 `127.0.0.1`，数据仍然是本机上的明文文件。这一点必须同时写在界面文案和帮助文档里，避免用户误以为"加了登录就等于加密"。

### 为什么不做成"网页多用户"

- `PRODUCT.md` 的硬约束是「不绑定公网、不引入远程控制端点」；一旦做注册登录，就要处理 HTTPS、跨用户限流、凭证托管、备份、计费，成本高一个量级。
- 现有 Playwright 是**本机浏览器**，多租户意味着服务器上并发跑多个抖音会话，风控和资源都是新问题。
- 本地多用户能覆盖 90% 的真实诉求：家里共用一台电脑、宿舍、共用工作机。

如果要走云端多用户，这是另一个产品，建议单独立项，不要和这一版混在一起。

### 三个关键决定

| # | 决定 | 原因 |
| --- | --- | --- |
| 1 | 账号层级为 `成员 → 工作区 → 抖音账号`，抖音账号从应用级下沉到成员级 | 复用现有 `app/accounts.py` 与 `account_paths(account, root)`，只是把 root 换成成员目录 |
| 2 | 认证用**本地密码 + 内存会话**，不引数据库、不引 JWT | 单机单进程，重启即失效更安全；零新依赖 |
| 3 | 定时任务仍然是**一条系统任务**，按成员分别判定是否到点，浏览器全局串行 | 避免维护 N 条 launchd / schtasks / crontab，删除成员也不用清理系统任务 |

## 2. 场景界定

| 场景 | 是否由本方案解决 |
| --- | --- |
| 同一台电脑、**同一个系统登录账号**，几个人轮流用 | ✅ 本方案 |
| 同一台电脑、**不同 macOS/Windows 账号** | 已经天然隔离（数据在各自的 Application Support 下），不需要本方案 |
| 想从手机上远程查看 | ❌ 不属于本地多用户，另做 |
| 防止懂技术的人看别人的数据 | ❌ 只能靠系统账号 / 磁盘加密 |

文档里要明确写：**登录密码防的是"顺手打开看看"，不是"有备而来的读取"。**

## 3. 概念模型与权限

```
本机 (DATA_ROOT)
└── 成员 User ──1:1── 工作区 Workspace
                     ├── 抖音账号 Account 1..n
                     │     ├── 好友 / 消息 / 发送规则
                     │     ├── 登录凭证 storage-state
                     │     └── 运行记录 / 截图 / trace
                     └── 自动任务设置 + 补跑状态
```

沿用现有的「多抖音账号」：它从"应用级"下沉为"成员级"。每位成员可以继续拥有多个抖音账号，互不共享。

### 3.1 角色

只有两种角色，不做更细的 ACL：

| 能力 | 管理员（第一个成员） | 成员 |
| --- | --- | --- |
| 登录 / 退出 / 改自己的昵称和密码 | ✅ | ✅ |
| 自己的抖音账号、好友、消息、任务、记录 | ✅ | ✅ |
| 添加 / 停用 / 删除成员 | ✅ | ❌ |
| 重置他人密码、生成临时密码 | ✅ | ❌ |
| 查看他人好友昵称、消息内容、凭证 | ❌ 永远不允许 | ❌ |
| 在「用户与成员」看到他人的数量与状态 | ✅（只有数量/进度/最近登录） | ❌ 页面不可见 |
| 切换成员 | ✅（需对方密码） | ✅（需对方密码） |

关键设计：**管理员也看不到别人的内容**，只能看到"有几个人、几个账号、今天发没发"。否则多用户就没有意义了。

### 3.2 不变量（实现时必须断言）

1. 始终至少保留 1 个启用状态的管理员：不能删除或停用最后一个管理员。
2. 成员被停用后：不能登录、不能切换进去、自动任务跳过，但数据保留。
3. 成员被删除：先停掉其正在运行的子进程，再决定数据去留。
4. 任何 API 都必须以会话身份解析数据根，**禁止**从请求参数里取 `userId` 去读别人的目录。
5. 会话过期或成员被停用后，下一次请求返回 `401`，前端回到登录页并提示原因。

## 4. 数据布局与迁移

### 4.1 现状

```
DATA_ROOT/
  config.json                 # 主账号任务配置
  config/accounts.json        # 多抖音账号注册表
  config/tasks/<id>.json
  storage-state.json / storage_state/<id>.json
  artifacts/                  # 历史、截图、日志、run.lock
  images/
  .env / .env.account-<id>
  .schedule.json              # 全局：每天几点跑
```

`ui/server.py` 里 `DATA_ROOT`、`REGISTRY`、`CONFIG`、`ARTIFACTS`、`STATE_FILE` 都是模块级常量，`account_paths(account, DATA_ROOT)` 直接拼绝对路径。

### 4.2 目标

```
DATA_ROOT/
  config/users.json                  # 成员索引：id/名字/角色/哈希/状态，0600
  .run.lock                          # 新的全局浏览器锁（跨成员串行）
  .scheduler.json                    # 系统任务自身的状态（下次检查、最后修复时间）
  users/
    youmi/
      .env                           # 原有 .env 移进来
      config.json
      config/accounts.json
      config/tasks/*.json
      storage_state/*.json
      images/
      artifacts/                   # 历史 + run.lock（成员内串行）
      .schedule.json               # 成员自己的运行时间
    ache/
      ...
```

`users.json` 只放登录所需的最小信息，好友、消息、凭证一律不进索引文件：

```json
{
  "version": 1,
  "users": [
    {
      "id": "youmi",
      "name": "小悠米",
      "role": "admin",
      "enabled": true,
      "can_schedule": true,
      "created_at": "2026-10-25T09:00:00+08:00",
      "last_login_at": "2026-10-25T09:12:00+08:00",
      "password": { "algo": "scrypt", "n": 16384, "r": 8, "p": 1, "salt": "…", "hash": "…" },
      "must_change_password": false
    }
  ]
}
```

### 4.3 代码改动点

`app/accounts.py` 不动（它本来就接收 `project_root`），只改调用方：

```python
# ui/server.py 之前
paths = account_paths(account, DATA_ROOT)
# 之后
paths = account_paths(account, user_root(session.user_id))
```

需要逐个改成"按会话解析"的地方：

| 位置 | 现在 | 改成 |
| --- | --- | --- |
| `build_state()` | `DATA_ROOT` | `user_root(uid)` |
| `account_overview()` | 全局注册表 | 当前成员的注册表 |
| `write_registry()` / `ensure_registry_for_add()` | 根目录 | `users/<uid>/config/accounts.json` |
| `/api/images/*` | `DATA_ROOT/images` | `users/<uid>/images`，并校验 uid 前缀 |
| `Runner.start()` | `DOUYIN_DATA_DIR` | 追加 `DOUYIN_USER_ID`，子进程按成员解析 |
| `run_history()` / `last_run()` | 传入 paths | 传入当前成员的 paths |
| `.schedule.json` | 根目录 | `users/<uid>/.schedule.json` |
| launchd/cron/计划任务 | 1 条 | 1 条（见第 6 节，不要按成员建多条） |

> 建议：不要在每个函数里临时拼路径，统一加一个 `paths_for(uid) -> UserPaths` 值对象，测试里可以直接断言"两个成员拿到的根目录不相等"。

### 4.4 升级迁移（必须一次成功）

1. 启动时检查 `config/users.json` 是否存在；不存在且根目录有 `config.json` / `config/accounts.json` / `storage-state.json` 等旧数据 → 进入「首次设置」全屏页。
2. 用户填写昵称和密码 → 创建管理员 `owner` → 执行迁移：
   - 先 `DATA_ROOT/users/owner/` 建目录；
   - 用 `shutil.move` 逐个搬 `config.json`、`config/`、`storage_state*`、`storage-state.json`、`artifacts/`、`images/`、`.env*`、`.schedule.json`；
   - 写入 `users/owner/.migration.json`（版本、时间、搬了哪些路径）；
   - 全部成功后才写 `config/users.json`；
   - 任一步失败 → 按记录逆序搬回，并提示"迁移失败，原数据未改动"。
3. 迁移完成后旧路径不再读取；界面首次进入时提示"已把原来的账号数据迁移到你的名下"。

注意事项：

- 读取旧数据的**早于**迁移写入，任何异常都不能留下"一半新一半旧"的状态；迁移期间加 `DATA_ROOT/.migration.lock`，防止两个进程同时搬。
- `storage-state.json` 等敏感文件移动后保持 0600。
- 迁移是**一次性**的；之后新增成员一律走空工作区。

## 5. 登录、会话与密码

### 5.1 密码

- 用标准库 `hashlib.scrypt(password, salt, n=2**14, r=8, p=1, dklen=32)`，每用户 16 字节随机 salt。
- 校验用 `hmac.compare_digest`，失败也走一遍完整哈希，避免时间侧信道。
- 规则：至少 6 位、不能全是空格、不能等于昵称。不强制定期更换。
- 任何日志、异常、接口响应里都不得出现密码或哈希。

### 5.2 会话

本机单进程应用，不引 JWT，也不引数据库：

- 服务端内存 `sessions: dict[token, {uid, expires, created_at}]`，`secrets.token_urlsafe(32)`。
- Cookie：`douyin_fire_session`，`HttpOnly; SameSite=Strict; Path=/`，默认 12 小时；勾选"保持登录"则 30 天。
- 应用退出即清空（内存态），重启后需要重新登录 —— 这比"持久 token"更符合本地工具的预期。
- CSRF：已有的 `origin_ok()` + `SameSite=Strict` 足够；新增的 `/api/auth/*` 同样走这个校验。
- 写入类接口额外要求 `Content-Type: application/json`，减少表单跨站提交面。

### 5.3 限流

- 每个成员连续失败 5 次 → 该成员冷却 60 秒；成功登录清零。
- 全局每分钟最多 20 次登录尝试。
- 失败提示统一为"密码不正确"，不区分"没有这个成员"，避免枚举（本地场景风险低，但顺手做了）。

### 5.4 单人模式

只有 1 个成员且没有设置密码（或关闭了"启动需要登录"）时，直接进入工作区，不显示登录页。

- 升级用户默认走这条路径：迁移时不强制设密码，设置页里可以随时开启。
- 一旦添加了第 2 个成员，强制要求所有人设密码，否则分区没有意义。

### 5.5 忘记密码

| 情况 | 处理 |
| --- | --- |
| 成员忘了 | 管理员在成员页「重置密码」→ 生成 8 位临时密码，只显示这一次，`must_change_password=true`，对方登录后必须先改 |
| 管理员忘了 | 提供文档级恢复：关闭应用 → 编辑 `config/users.json` 删除该用户的 `password` 字段并保留 `role: admin` → 重启走"设置新密码"。需要文件访问权限，和"能改数据"是同一权限级，不假装更安全 |
| 全部成员丢失 | 同上，任何一个人都能通过文件恢复成管理员 |

### 5.6 会话与"正在运行"

- 自动任务在**子进程**里跑，不依赖登录状态；没人登录也会按时执行。
- 前端顶部的"运行中"来自全局锁文件 `DATA_ROOT/.run.lock`（见 6.3），而不是 `RUNNER` 单例，这样别人触发的运行也能显示。

## 6. 定时任务与并发（这次真正的难点）

### 6.1 现状

- 每个安装只有一条系统任务：macOS `~/Library/LaunchAgents/com.meiyh.douyin-auto-fire.plist`、Windows 计划任务、Linux cron。
- plist 里是 `StartCalendarInterval`（每天固定时刻）+ `StartInterval 1800`（每 30 分钟补跑一次）。
- 命令是 `run --catch-up --not-before HH:MM`，只跑"当前 DATA_ROOT"这一份数据；`catch-up.json` 记录当天跑没跑过、跑了几次。
- 全局只有一个浏览器进程（`Runner` 单例），账号之间串行。

### 6.2 推荐方案：一条系统任务，按成员分别判定

不要为每个成员建一条系统任务。原因：删除成员时要清理 plist / schtasks / crontab，容易残留；而且 Electron 是单实例，多条任务最后都会转发到同一个进程，收益为零。

改成：

1. 系统任务保持 1 条，把 `StartInterval` 从 1800 改为 **600（10 分钟）**，`StartCalendarInterval` 保留为"最早成员的运行时间"（可选项，纯粹为了准点）。
2. `--scheduled-run` 的处理逻辑改为"遍历所有启用的成员"：
   ```
   for user in enabled_users:
       if not user.can_schedule: continue
       schedule = read(user/.schedule.json)      # hour, minute, enabled
       if not due(schedule, now): continue        # 未到点
       if already_ran_today(user): continue       # 复用现有 catch-up 判定
       acquire_global_lock(user)
       run_one_user(user)                         # 子进程，串行
       release_global_lock()
   ```
3. 每个成员沿用现有的补跑语义（当天最多 3 次、30 分钟检查点、失败好友只补发失败的），只是 `catch-up.json` 落在 `users/<uid>/artifacts/` 下。
4. 界面文案同步调整：`每天 07:00` → `每天 07:00 起（10 分钟内开始）`。这是这个方案唯一的体验代价，换来的是"不用维护 N 条系统任务"。

为什么 10 分钟：判定逻辑只是读 JSON，开销可以忽略；对用户来说"到点后 10 分钟内开始"和"准点"几乎无感；出错时补跑也更及时。

### 6.3 并发：一个浏览器，一个队列

- 新增 `DATA_ROOT/.run.lock`，内容 `{"uid": "...", "account": "...", "pid": 1234, "started_at": "..."}`，`O_CREAT|O_EXCL` 创建，进程退出/被强杀时按 `pid` 存活检测回收（复用 `app/history.py:run_lock` 的思路）。
- 成员内仍然保留原来的 `users/<uid>/artifacts/run.lock`（防同一成员的两个账号并发）。
- 抢不到全局锁时：每 30 秒重试，最多等 10 分钟；超时就退出，等下一个 10 分钟检查点补跑。
- 同一时刻最多 1 个 Chromium：这是硬约束，多人同时段运行会顺延，UI 上要说明"撞时间会排队"。

### 6.4 与现有功能的冲突点

| 现状 | 多成员后 |
| --- | --- |
| `--scheduled-run` 假定单一数据根 | 改为遍历成员，命令要带 `DOUYIN_USER_ID` |
| 定时运行不依赖登录（无会话） | 保持：调度入口用文件系统直接读，不查会话 |
| 界面"运行中"读 `RUNNER` | 补一条：读 `.run.lock` 显示"其他成员正在运行" |
| 成员停用 | 调度直接跳过，并取消其系统任务里的"准点"语义（不需要动系统任务） |
| 成员删除 | 停止其子进程 → 可选举措：保留/删除 `users/<uid>/` |
| `StartCalendarInterval` 只有一个时间 | 保留主人时间做准点触发，其他人靠 10 分钟轮询 |

### 6.5 备选方案（不推荐，但记录）

**每成员一条系统任务**：准点、互相独立，但要在 macOS 维护 N 个 plist、Windows N 个计划任务、Linux N 行 crontab；删除成员要清理；AppImage 下 `--scheduled-run` 还要透传 uid。除非将来成员数固定且很少（比如 2 人），否则不值得。

## 7. 页面与交互（对应效果图）

效果图见 [`preview.png`](design/multi-user/preview.png)，三块画面：登录、用户与成员、关键弹层。

### 7.1 登录（全屏，无侧栏）

- 位置：未登录 / 会话过期 / 成员被停用时全屏出现。
- 结构：品牌 → 「本机 · N 位成员」→ 大标题 → 一行成员头像卡（选中态蓝框 + 勾）→ 密码 → 登录 → 帮助文案。
- 细节：
  - 上次登录的成员默认选中，减少日常操作。
  - 密码框回车即提交；「显示密码」用图标切换。
  - 失败提示用轻提示（底部深色条），不清空已输入的昵称选择，只清空密码。
  - 停用成员不出现在登录页；如果只剩 1 个成员，直接显示密码框，不显示头像行。
  - 页脚固定两句话：`本地运行 · 数据不离开这台电脑`、版本号。

### 7.2 首次设置（迁移时）

同一个登录页的变体：标题「设置你的账号」→ 昵称 + 密码 + 确认密码 → 按钮「创建并迁移数据」→ 下方小字说明"原来的好友、消息、登录状态会搬到你这个账号下"。

不单独做引导页，避免升级用户多点几屏；但迁移失败要有明确的中文错误和"原数据未改动"的保证。

### 7.3 用户与成员（管理员页，`#/users`）

侧栏新增一组「本机」，位于五个工作区页面之下，与"工作区"分组区分开。这一组只有管理员能看到；成员登录后换成「个人设置」。

页面从上到下：

1. **页头**：眉题「本机 · N 位成员」、标题「用户与成员」、一句说明、右侧主操作「添加成员」。
2. **身份卡**：自己的头像、昵称、角色徽标、上次登录时间；右侧「修改密码」「退出登录」；底部三格：我的抖音账号、今日已发送、每日自动运行。这三格回答"我现在是什么状态"，不做假数据。
3. **成员列表**：表头「成员 / 抖音账号 / 今日进度 / 最近登录 / 操作」。
   - 成员列：头像（首字）、昵称、角色徽标、加入时间；自己带「我」小标。
   - 抖音账号列：只显示**数量**和"是否登录有效"，绝不显示账号昵称——否则等于泄露别人发了什么。
   - 今日进度列：`3/5` + 6px 细进度条，不做百分比大数字。
   - 操作列：`切换`（次要按钮）+ `⋯`（重命名 / 重置密码 / 停用 / 删除）。
   - 停用行整行降级为灰字，操作换成「启用」。
4. **底部两张说明卡**：一张讲"这是分区不是保险箱"，一张讲"自动任务按成员排队"。

空状态：

- 只有自己一个人：成员列表下方提示"这台电脑只有你在用？可忽略此页"，并在身份卡里给"启动时要求登录"的开关。
- 全部成员都停用（不可能出现，最后一名管理员不能停用）——不需要设计。

### 7.4 侧栏用户块与切换弹层

- 用户块放在侧栏底部「运行状态卡」之上：34px 头像 + 昵称 + 角色 + 向上箭头。
- 点开向上弹出：标题「切换用户」+ 右上「共 N 人」；每行头像 + 昵称 + 最近登录；未解锁的行右侧是锁图标；底部「管理成员 →」与「切换需输入密码」。
- 点未解锁的成员 → 弹出密码输入框（一个小弹层，不跳页），输入正确直接切换；错误就抖动 + 提示，不关闭弹层。
- 切换后：关闭所有打开的对话框、清空当前页状态、跳到该成员的首页、轻提示"已切换到 阿澈"。
- 有任务正在运行也可以切换：运行在子进程里，不受会话影响；弹层里提示"阿澈的任务正在运行，切换不会中断"。

### 7.5 三个关键弹层

| 弹层 | 关键点 |
| --- | --- |
| 添加成员 | 昵称、密码、确认密码、`允许使用自动任务`开关；说明"新成员要自己扫码登录抖音"；创建后**不**自动切换 |
| 重置密码 | 二次确认 → 生成 8 位临时密码 → 等宽字体展示 + 复制按钮 → "只显示这一次"的提示 |
| 删除成员 | 输入成员名字确认 + 单选「保留数据（推荐）/ 一并删除」+ 琥珀色说明"只移除本机入口，不影响对方抖音账号" |

危险操作的通用规则：主按钮红色、默认聚焦在「取消」、按 Esc 关闭、不可点遮罩关闭（防止误触）。

### 7.6 移动端 / 窄屏

- 900px 以下：侧栏变成底部导航，用户块移到顶部品牌栏右侧（头像按钮），点头像弹出同一个切换面板。
- 680px 以下：成员表改成卡片行（头像 + 昵称 + 角色 / 账号数 / 今日进度 / 操作），删除与停用收进 `⋯`。
- 登录页在手机上卡片满宽、去掉背景留白，键盘弹起时按钮不被遮挡。

### 7.7 文案基调

- 说人话，不用"租户""实例""RBAC"。
- 涉及风险的句子必须具体：不写"数据安全"，写"文件没有加密，能打开这台电脑文件夹的人可以读到"。
- 不承诺"绝对隔离"。

## 8. 接口草案

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/session` | 当前会话：`{authenticated, user:{id,name,role}, needsSetup, memberCount, requirePassword}` |
| POST | `/api/auth/setup` | 首次创建管理员并触发迁移（仅当无人时可用） |
| POST | `/api/auth/login` | `{userId, password, remember}` → 设置 Cookie |
| POST | `/api/auth/logout` | 清会话 |
| POST | `/api/auth/password` | `{old, new}` 改自己的密码 |
| GET | `/api/users` | 管理员：成员列表（含数量/进度/最近登录，不含内容） |
| POST | `/api/users` | 添加成员 `{name, password, canSchedule}` |
| POST | `/api/users/update` | 重命名 / 停用 / 启用 / 允许自动任务 |
| POST | `/api/users/password` | 管理员重置，返回一次性临时密码 |
| POST | `/api/users/remove` | `{id, deleteData}` |
| POST | `/api/auth/switch` | 与 login 同义，语义上用于切换（要重新校验密码） |

所有既有 `/api/*` 都要求会话；未登录统一 `401 {"error":"unauthenticated"}`。前端收到 401 → 清空本地状态 → 显示登录页。

`GET /api/stream` 也要按会话过滤：成员只能收到自己账号的事件，不能收到别人的日志行。

## 9. 边界与风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 迁移中断 | 用户数据"消失" | 先搬后写索引 + 失败逆序回滚 + `.migration.lock` |
| 多人同一时段运行 | 排到 10 分钟后，或撞车 | 全局锁 + 有界等待 + 补跑；界面说明"会排队" |
| 密码遗忘 | 进不去 | 管理员重置；管理员自己忘了走文件恢复 |
| 明文凭证 | 同机可读 | 文案明确；后续可选接入系统钥匙串（macOS Keychain / Windows DPAPI） |
| 多人共用窗口的会话串号 | A 的页面看到 B 的数据 | 每次请求都从 Cookie 取会话，前端切换后整体重载状态；禁止把 uid 放 URL |
| 删除成员时正在跑 | 子进程残留 | 先检查 `users/<uid>/artifacts/run.lock` 的 pid，必要时终止并回收锁 |
| 成员数量失控 | 数据目录膨胀 | 可选上限（如 8 人），超限时提示 |

另一个必须接受的事实：**同一系统账号下，文件权限相同**。任何"把 users/ 设成 0700 就安全了"的说法都是错的——所有成员都由同一个 OS 用户启动，权限位压不住。要么接受，要么引导用户用系统账号。

## 10. 实施拆分（建议顺序）

每一步都能独立合并、独立回滚。

### Step 1 · 数据分层与迁移（约 1.5 天）

- 引入 `UserPaths` / `user_root(uid)`，把 `build_state`、`account_overview`、`write_registry`、图片路由、`Runner` 全部改成按会话/uid 解析。
- 实现一次性迁移 + 回滚 + `.migration.lock`。
- 测试：两个成员各自读写互不影响；迁移后旧数据仍可正常发送；迁移中断可回滚。

### Step 2 · 认证（约 1 天）

- `config/users.json` 读写、scrypt 哈希、内存会话、Cookie、限流。
- 登录页 + 首次设置页 + `401` 处理。
- 测试：错误密码 5 次限流；会话过期；停用成员登录被拒；单人模式免登录。

### Step 3 · 成员管理（约 1.5 天）

- `/api/users*` 与权限校验；成员页；侧栏用户块 + 切换弹层；三个对话框；空状态；移动端。
- 测试：成员调用管理接口返回 403；最后一个管理员不可删除；删除时数据保留/清理。

### Step 4 · 调度与并发（约 2 天，风险最高）

- 调度遍历成员 + 每成员 `.schedule.json` + 全局锁 + 等待/补跑。
- 界面显示"其他成员正在运行"。
- 测试：两个成员同时到点只跑一个；等待超时后下一轮补跑；停用成员被跳过。

合计约 6 个工作日，不含真机回归（Windows 计划任务、Linux cron、AppImage 各跑一遍）。
