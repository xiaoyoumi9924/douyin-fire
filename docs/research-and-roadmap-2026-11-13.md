# 抖音自动续火花：同类项目调研与优化路线

调研日期：2026-11-13（北京时间）。本地基线：`bfc7a73`，应用版本 `0.1.7`。

后续范围调整：用户已明确取消 AI 文案与视频回复草稿，不纳入开发计划。下面的同类项目资料保留作调研记录。

本轮完成公开资料检索、代表仓库 README / Issues / PR 阅读、本地核心链路审阅和现有测试验证。没有登录抖音、发送私信或更改系统定时任务；本轮仅新增本文件。原有未跟踪的多成员方案及设计文件保留原样。

## 1. 建议结论

继续发展为「本地运行的个人续火助手」。保留 Electron + Python + Playwright，优先补齐定时可靠性、好友识别、消息规则和诊断闭环，再增加可选 AI 能力。当前没有重写整套框架或搬到云端的充分理由。

建议首批范围：**修复调度问题 → 同步聊天列表并绑定好友 → 好友专属消息 → 登录健康与失败处理中心**。

本地测试结果：`253 passed in 11.71s`。这说明已有测试通过，不代表当前抖音网页、各系统安装版和真实消息送达已经端到端验证。

## 4. 已发现的问题与优化机会

### A. Linux 设定时间与实际检查时间不一致——优先修复

依据：`ui/server.py:311` 的 `_apply_linux_schedule()` 只安装 `*/30 * * * *`，设定时刻仅通过 `--not-before` 传入。

例子：设置 08:05，08:00 检查会跳过，下次到 08:30 才开始。电脑一直开机也会延后，属于代码可确定的行为；本轮没有实际安装 cron。

方案：增加精确到设定分钟的触发，保留周期补跑；或采用支持持久补跑的 systemd 用户 timer。前者变更较小。验收至少覆盖 08:00、08:05、08:59、错过时刻后恢复，以及两个触发同时到达的去重。

### B. AppImage 已打开时，二次启动参数丢失——优先修复

依据：`desktop/main.cjs:41` 的 `second-instance` 收到新 `argv`，但调用 `requestScheduledRun()` 没有传入它；后续 `scheduledRunFlags()` 从主进程旧 `process.argv` 取参数。

本轮提取原参数解析函数做无副作用复现：主窗口正常启动，新调用携带 `--scheduled-run --catch-up --not-before 08:05`，得到的 payload 却是 `{"catchUp":false}`，并缺少 `notBefore`。Linux 周期任务因此可能绕过“尚未到时间”的门禁。现有消息历史仍提供去重保护，不能据此断言已发生重复发送。

方案：参数解析函数显式接收 argv；把完整请求作为待执行对象保存，不用一个布尔值表示待调度任务。验收同时覆盖窗口已打开、后端尚未就绪和冷启动三种路径。

### C. 登录状态目前只是“凭证文件存在”

依据：`ui/server.py:633` 的 `credential_state()` 返回文件存在性和修改时间；真正的登录验证在浏览器运行时执行。

方案：分成“未配置 / 未验证 / 最近验证可用 / 已失效 / 需要安全验证 / 检查失败”，记录验证时间与原因。网络失败不能直接覆盖为登录过期，不使用固定天数猜测 Cookie 有效期。

### D. 好友身份和去重仍依赖名字

依据：`Target` 只有 `name` 与 `messages`；聊天搜索与标题确认按名字进行；历史键包含 `target.name` 和消息内容摘要。

这不是已经观察到的错发，但存在改名、同名和当天改文案后去重键改变的边界。建议引入应用内部稳定 `target_id`、单独的 `display_name` / `lookup_name`；若页面可靠提供会话标识再保存。不能把“内部生成 UUID”当成已经证明对方身份。

有可靠会话 ID 时验证 ID；只有姓名时若匹配到多个候选，停止并要求重新绑定。昵称变化应更新展示字段，不应自动解除当天去重。

### E. 专属消息后端基础已存在，面板尚未完整表达

依据：`load_task()` 支持 `targets[].messages`；面板 `/api/friends` 和 `/api/message` 主要写入全局 `friends` / `messages`，`message_state()` 也主要读取全局消息。

方案：增加“默认消息 + 好友覆盖”的可视化编辑。先统一配置模式及转换规则，再改界面，避免新旧结构同时存在而编辑不生效。随机候选应在准备阶段确定并保存，后续重试使用同一份已准备内容。

### F. 调度健康展示与文件增长

- `schedule_command_matches()` 在非 macOS 或非打包路径直接返回 True；Windows/Linux 的面板状态不能充分证明系统任务实际存在且命令正确。
- `run-history.jsonl` 已限制最近 30 次；但 `history.json` 持续积累消息键，截图、trace、桌面后端追加日志在已审阅路径中未见统一保留策略。
- 建议补实际系统任务查询、最近触发/退出原因，增加按类型的保留期限与容量上限。清理不得破坏当天去重和未解决的 unknown 记录。

## 6. 推荐的首批功能设计

### 6.1 同步聊天列表

入口：好友管理 → 同步聊天列表 → 显示候选 → 用户勾选 → 预览新增与变化 → 保存。

默认只同步当前账号可见的聊天会话，不承诺获取完整好友通讯录。复用已有浏览器与互斥机制，分页/虚拟滚动限时终止；返回本次是否完整、是否被截断。名称、头像、会话标识、火花信息均允许缺失。

同步是增量合并，不自动删除旧好友、不自动启用新好友。同名、标识冲突和改名结果进入待确认列表；头像只能辅助识别，不能充当唯一身份凭据。

### 6.2 默认消息与专属规则

消息管理保留默认消息；好友详情增加“继承默认 / 专属文案 / 暂停自动发送”。第一版支持单条文字、单张图片、从候选随机一条，暂不叠加复杂规则编辑器。

配置增加版本号，逐步使用稳定 target_id 和 rule_id。建议默认一个好友每天一个续火槽位，规则编辑不自动产生第二条消息；未来需要多时段时，再显式引入 slot_id。发送前先持久化已解析文案与候选选择，结果不明时仍禁止自动换句重发。

旧历史迁移必须保守：能可靠映射就沿用当天状态，无法映射则标待核对，不能把旧记录清空当作尚未发送。群聊与个人会话需要明确区分，保留已有兼容性。

### 6.3 健康与待核对中心

概览只突出四件事：登录是否可用、今天哪些人已发送、哪些失败/待核对、下一次何时检查。

错误分为登录失效、安全验证、目标无法确认、网络暂时失败、发送明确失败、发送结果不明、系统任务异常，并给出相应操作。unknown 的操作为“打开抖音核对 → 确认已发送 / 确认未发送”；选择未发送后再单独触发补发并留审计记录，不能用“重置全部今日记录”代替。

通知优先仅报失败、待核对和登录失效，避免每次补跑检查都打扰用户。消息发送状态和火花观测状态分开显示；本程序确认发送，不代表平台已确认火花续上。

## 7. 实现顺序与验收

1. **调度修复**：先完成 Linux 分钟精度与 AppImage 参数透传；覆盖冷启动、已打开窗口、后端准备中、同时触发、休眠恢复。窗口内任务与系统直接启动的任务都要检查锁语义。
2. **配置与身份升级**：版本化配置、稳定内部 ID、旧历史映射；为改名、重排、当天改文案、重名和随机重试建立回归验证。
3. **聊天列表同步与专属消息**：先在本地模拟页面验证列表滚动、重复行、缺失字段和搜索歧义，再进行受控的真实网页适配验证。
4. **健康中心与诊断**：不发送的登录检查、系统任务状态查询、错误分类和 unknown 处理；历史中保留用户核实记录。
5. **体验与扩展**：通知、备份、保留策略；之后根据需求选择 AI 或多成员，不必同时上。

保持现有运行模块，逐步把 `ui/server.py` 中的调度、账号存取、任务状态组织成可测试的服务；前端按实际功能拆分，避免把大规模重构作为所有新功能的前置条件。JSON 当前可以继续使用；出现持久队列、多成员事务或历史查询需求后，再评估 SQLite。

浏览器适配优先减少固定等待，使用定位器与可观察条件；对确实没有稳定可访问属性的页面保留受控 CSS 回退，不盲目删除现有适配。依据：[Playwright 定位器](https://playwright.dev/python/docs/locators)、[自动等待](https://playwright.dev/python/docs/actionability)。

## 8. 产品边界与待验证事项

- [抖音官方主动私信能力](https://developer.open-douyin.com/docs/resource/zh-CN/mini-app/open-capacity/operation/private-account/private-message) 要求关联企业机构账号并获得接收方授权。按该文档，不能把它直接当成本项目普通个人好友续火的通用替代接口。
